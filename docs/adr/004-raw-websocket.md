# ADR-004 WebSocket은 STOMP 없이 그대로 쓴다

날짜 2026-10-12 · 상태 채택 · 관련 ADR-003

## 맥락

방 안 상태는 2초 안에 서로 보여야 한다 (N-06). `03-api.md` 10절이 `/ws` 주소와 `{ "type", "data" }` 메시지 모양, 첫 메시지 `auth`, 30초 `ping`까지 이미 정했다.
Spring에서 실시간을 하는 방법이 몇 가지 있다.

## 선택지

| 안 | 내용 | 걸리는 점 |
|---|---|---|
| A. WebSocket + STOMP (`@MessageMapping`, SimpleBroker) | Spring 문서가 제일 많이 미는 방식. 구독/발행이 내장 | 토픽·구독 계층이 API 문서의 메시지 모양과 겹친다. 프론트도 STOMP 클라이언트가 필요 |
| B. WebSocket 그대로 (`WebSocketHandler`) | JSON 메시지를 직접 읽고 쓴다 | 방 → 연결 목록 관리를 직접 짠다 |
| C. SSE (서버 → 브라우저만) | HTTP라 단순. 프록시 통과가 쉽다 | 한 방향이라 `presence.update`, `ping`은 REST로 따로 보내야 한다. 연결 끊김 감지가 어색해진다 |

## 결정

B.

## 이유

API 문서가 메시지 모양을 이미 정해 뒀다. STOMP를 얹으면 `/topic/rooms/{id}` 같은 주소 체계가 하나 더 생기고 문서를 다시 써야 한다.
방이 최대 30명이고 사용자당 연결 하나다. 방 ID → 연결 목록 맵과 for문이면 끝난다. 브로커가 할 일이 없다.
C도 괜찮았다. 하지만 `ping`으로 끊김을 잡는 설계가 있어서 양방향이 자연스럽다. 그리고 WebSocket 핸들러를 직접 짜 보는 게 "실시간 통신"을 배우는 데 더 가깝다. STOMP는 그걸 가려 버린다.

## 감수하는 것

- 연결 관리(들어오고, 나가고, 끊기고)를 직접 한다. `RoomPresenceRegistry` 한 클래스에 모아 두고 단위 테스트를 붙인다
- Caddy가 `/ws`를 WebSocket으로 넘기도록 설정해야 한다. Caddy는 기본으로 되지만 타임아웃 값을 확인한다
- 서버 두 대가 되면 다른 서버에 붙은 사람에게 못 보낸다 → ADR-003

## 다시 볼 조건

메시지 종류가 지금(10개)의 몇 배로 늘어 라우팅이 지저분해질 때. 그때는 STOMP가 정리해 준다.
