# ADR-003 Redis는 서버가 두 대가 될 때까지 안 둔다

날짜 2026-10-12 · 상태 채택 · 관련 ADR-002, ADR-004

## 맥락

Redis를 쓸 만한 자리가 세 군데 보인다.

1. 방 안 사람들의 지금 상태(`focusing`, `resting`...). DB에 안 쓰기로 했다 (`03-api.md` 10절)
2. 요청 횟수 제한 카운터
3. AI 하루 한도 카운터

그리고 "Spring + Redis"는 흔한 조합이라 배워 두면 좋다는 생각도 있었다.

## 선택지

| 안 | 내용 | 걸리는 점 |
|---|---|---|
| A. 처음부터 Redis | 위 셋을 Redis에. 서버 두 대 확장이 바로 된다 | 서버 한 대에서는 아무 이득이 없다. 띄우고 관리할 게 하나 는다 |
| B. 지금은 메모리, 두 대 될 때 Redis | 방 상태는 `ConcurrentHashMap`, 횟수 제한은 Bucket4j 메모리, AI 한도는 DB 행 수 | 두 대로 갈 때 세 군데를 고쳐야 한다 |

## 결정

B.

## 이유

ADR-002에서 서버는 한 대다. 한 대에서 Redis는 "메모리를 네트워크 너머에 두는 것"이라 느려지기만 한다.
방 상태는 날아가도 된다고 API 설계에서 이미 정했다. 재연결하면 `room.snapshot`으로 다시 받는다. 그러니 재시작에 살아남는 저장소가 필요 없다.
AI 한도는 "오늘 몇 번 썼나"인데 `coach_messages`를 날짜로 세면 나온다. 카운터를 따로 두면 둘이 어긋날 수 있다.
"배우려고 넣는다"는 이유는 버렸다. 쓰는 곳이 없는 인프라는 왜 있는지 설명이 안 된다. 두 대가 될 때 넣으면 그때는 설명이 된다.

## 감수하는 것

- 서버를 두 대로 늘리는 순간 아래가 깨진다. 그래서 코드에서 셋을 각각 인터페이스 뒤에 둔다
  - `RoomPresenceRegistry` → Redis Hash + Pub/Sub 구현으로 교체
  - Bucket4j 메모리 → Bucket4j Redis(Lettuce) 백엔드로 교체
  - `@Scheduled` → ShedLock 추가 (두 대가 같은 작업을 두 번 안 하게)
- 재시작하면 방 상태와 횟수 제한 카운터가 초기화된다. 재시작 직후 잠깐 제한이 느슨해지는 건 받아들인다

## 다시 볼 조건
